# 代码评审清单

评审目标不是“挑错”，而是**在合并前用最低成本拦住会进生产的缺陷**。按影响排序，先看正确性与安全，
再看设计与测试，最后看风格（风格交给工具，不占人工评审时间）。

## 0. 严重级别

| 级别 | 含义 | 处理 |
|---|---|---|
| **blocker** | 正确性/安全/数据损坏风险，或破坏公共 API | 必须修改后才能合并 |
| **major** | 明显缺陷或高维护成本，但非立即致命 | 应修改；不改需说明并开 issue |
| **minor** | 可读性/一致性建议 | 建议修改，可不阻塞 |
| **nit** | 个人偏好 | 不阻塞，作者可忽略 |

评审意见必须带级别前缀，例如 `blocker: ...`、`nit: ...`，避免作者猜测严重程度。

## 1. 通用（所有语言）

- [ ] 变更范围与 PR 描述一致，没有夹带无关改动
- [ ] 能编译/能运行，CI 全绿；新增警告为零
- [ ] 错误路径已处理：失败有返回值/异常/日志，不静默吞掉
- [ ] 边界条件：空输入、0、负数、最大值、超长、并发、重复调用
- [ ] 资源释放：文件、锁、线程、连接、临时目录
- [ ] 日志不含密钥/令牌/个人信息；错误信息含上下文
- [ ] 公共 API 有文档与示例；破坏性变更已标注
- [ ] 测试覆盖新增逻辑与缺陷场景；测试确定性
- [ ] 依赖新增有理由、许可证可接受、版本已锁定
- [ ] 无调试残留：`print` / `console.log` / 注释掉的大段代码 / TODO 无 issue

## 2. C++ 专项

- [ ] 无未定义行为：有符号溢出、越界、悬垂引用、空指针解引用、数据竞争
- [ ] 所有权清晰：无 owning 裸指针；`unique_ptr` 优先；`shared_ptr` 有共享理由
- [ ] Rule of Zero/Five：自定义析构/拷贝/移动是否配套；移动/析构是否 `noexcept`
- [ ] 生命周期：`string_view` / `span` / 引用未指向已销毁对象
- [ ] 并发：锁顺序一致、原子内存序有依据、无伪共享热点
- [ ] 异常策略与项目 Profile 一致；异常未跨越 C ABI/回调边界
- [ ] 热路径：无意外分配、锁、日志、虚调用；有 benchmark 佐证
- [ ] 整数与长度运算防溢出；外部输入已校验
- [ ] 头文件自包含、IWYU；无 `using namespace` 泄漏
- [ ] 格式化与 clang-tidy 通过

## 3. Python 专项

- [ ] 公共函数有类型注解；`mypy` 通过；`Any` 有理由
- [ ] 只捕获具体异常；`raise ... from` 保留因果链
- [ ] 无裸 `except`、无静默 `pass`
- [ ] 外部输入校验；`subprocess` 用列表且 `shell=False`
- [ ] 无 `eval` / `exec` / 不可信 `pickle` / `yaml.load`
- [ ] 依赖写入 `pyproject.toml` 且有锁文件
- [ ] 测试用 `tmp_path` / `monkeypatch`，无真实网络与裸 `sleep`
- [ ] 日志用 `logging`，库代码不配置 handler
- [ ] `ruff check` 与 `ruff format --check` 通过

## 4. Git / 流程

- [ ] 提交信息符合 Conventional Commits；type/scope 准确
- [ ] 一个 PR 一件事；重构/格式化与行为变更分离
- [ ] 无密钥、令牌、私钥、生产配置、大二进制入库
- [ ] 分支命名规范；已 rebase 到最新 `main`
- [ ] PR 描述含测试证据与回滚方式
- [ ] 破坏性变更已标注 `!` 或 `BREAKING CHANGE`，并更新 CHANGELOG

## 5. 评审者行为准则

- 先理解意图再评论；不确定时提问，而不是断言。
- 区分“必须改”和“可以更好”；不把个人偏好包装成规范。
- 给出可执行的建议或代码片段，避免“这里不好”。
- 对重复出现的问题，建议补进规范或 lint 规则，而不是每次口头提醒。
- 24 小时内给出首轮意见；无法及时评审时主动转交。
